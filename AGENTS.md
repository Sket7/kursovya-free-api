# AGENTS.md

## Назначение проекта

Нужно реализовать одно и то же Android-приложение-каталог по мультсериалу «Рик и Морти» в нескольких
архитектурных вариантах. Каждый вариант разрабатывается независимо в собственной Git-ветке, но
должен иметь одинаковые пользовательские возможности, визуальное поведение и модель данных, чтобы
архитектуры можно было корректно сравнить.

В ветке `main` поддерживаются общая документация, согласованное техническое задание, единая
дизайн-система и запускаемый каркас проекта. Функциональность приложения и код конкретной реализации
добавляются только после перехода в соответствующую архитектурную ветку.

## Ветки и архитектурные варианты

Для реализаций использовать отдельные ветки от `main`:

| Ветка                | Вариант                     | Основной принцип                                                                                                    |
|----------------------|-----------------------------|---------------------------------------------------------------------------------------------------------------------|
| `mvc`                | MVC (Model–View–Controller) | Разделить модели, отображение и контроллер пользовательских действий.                                               |
| `mvvm`               | MVVM                        | Состояние и действия экрана находятся во `ViewModel`, UI наблюдает за состоянием.                                   |
| `mvi`                | MVI (Model–View–Intent)     | Однонаправленный поток данных: Intent → обработка → новое immutable-состояние → View.                               |
| `clean-architecture` | Clean Architecture          | Разделить presentation/domain/data; бизнес-сценарии оформить как Use Cases, зависимости направлять внутрь к domain. |
| `di-koin`            | Dependency Injection с Koin | Показать построение приложения через DI и Koin.                                                                     |

Правила работы с ветками:

- не смешивать несколько архитектур в одной ветке;
- ветки создавать от актуального `main`;
- функциональные требования во всех ветках одинаковы;
- общие исправления ТЗ сначала вносить в `main`, затем переносить в архитектурные ветки;
- особенности архитектуры должны быть видны в структуре пакетов, направлении зависимостей и
  управлении состоянием, а не только в именах классов;
- ветка `di-koin` должна использовать Koin как центральный предмет варианта; в остальных ветках DI
  допустим только после отдельного решения, чтобы сравнение не теряло смысл.

## Источник данных

Приложение использует публичный **The Rick and Morty API** только в REST-режиме.

- документация: <https://rickandmortyapi.com/documentation>
- Base URL: `https://rickandmortyapi.com/api`
- транспорт: только HTTPS;
- методы документированного REST API: только `GET`;
- формат ответов: JSON;
- авторизация и API-ключ не требуются;
- корневой запрос `GET /api` возвращает ссылки на ресурсы `characters`, `locations`, `episodes`.

GraphQL endpoint существует, но в этом проекте не используется. Не привязывать логику к указанному
на сайте текущему количеству персонажей, локаций или эпизодов: данные API могут пополняться.

## Общая модель списков и пагинация

Запрос списка возвращает объект следующего вида:

```json
{
  "info": {
    "count": 826,
    "pages": 42,
    "next": "https://rickandmortyapi.com/api/character?page=2",
    "prev": null
  },
  "results": []
}
```

Поля `info`:

- `count: Int` — общее число результатов с учётом фильтров;
- `pages: Int` — общее число страниц;
- `next: String?` — полный URL следующей страницы или `null`;
- `prev: String?` — полный URL предыдущей страницы или `null`.

API возвращает до 20 элементов на страницу. Номер задаётся query-параметром `page`; без него
открывается первая страница. При сочетании пагинации, поиска и фильтров все активные query-параметры
должны сохраняться.

Общие формы получения ресурсов:

- список: `GET /{resource}`;
- один объект: `GET /{resource}/{id}` — JSON-объект;
- несколько объектов: `GET /{resource}/1,2,3` (документация также показывает форму `[1,2,3]`) —
  JSON-массив;
- список с фильтрами: `GET /{resource}?name=value&...`;
- несколько query-параметров объединяются через `&`, значения должны URL-кодироваться.

Не предполагать, что все ответы имеют одинаковую оболочку: `info/results` есть у списков, одиночный
endpoint возвращает объект, endpoint нескольких ID — массив. Клиент обязан обрабатывать HTTP-ошибки,
отсутствие результатов, пустые связи, `null` в пагинации, таймауты, отсутствие сети и ошибки разбора
JSON. Точная схема ошибки официальной документацией не гарантирована, поэтому не связывать UI с
конкретным текстом поля ошибки.

## REST API: Character

Маршруты:

- `GET /character` — страница персонажей;
- `GET /character/{id}` — персонаж по ID;
- `GET /character/1,2,3` — несколько персонажей;
- `GET /character?...` — поиск и фильтрация.

Query-параметры:

| Параметр  | Значение                                   |
|-----------|--------------------------------------------|
| `page`    | Номер страницы.                            |
| `name`    | Поиск/фильтр по имени.                     |
| `status`  | `alive`, `dead`, `unknown`.                |
| `species` | Вид персонажа.                             |
| `type`    | Тип или подвид.                            |
| `gender`  | `female`, `male`, `genderless`, `unknown`. |

Параметры можно комбинировать, например: `GET /character?name=rick&status=alive&page=2`.

Схема `Character`:

| Поле       | Тип                | Значение                                      |
|------------|--------------------|-----------------------------------------------|
| `id`       | `Int`              | ID персонажа.                                 |
| `name`     | `String`           | Имя.                                          |
| `status`   | `String`           | `Alive`, `Dead` или `unknown`.                |
| `species`  | `String`           | Вид.                                          |
| `type`     | `String`           | Тип/подвид; может быть пустой строкой.        |
| `gender`   | `String`           | `Female`, `Male`, `Genderless` или `unknown`. |
| `origin`   | `LocationRef`      | Имя и URL места происхождения.                |
| `location` | `LocationRef`      | Имя и URL последней известной локации.        |
| `image`    | `String (URL)`     | Аватар 300×300 px.                            |
| `episode`  | `List<String URL>` | Эпизоды с участием персонажа.                 |
| `url`      | `String (URL)`     | URL самого ресурса.                           |
| `created`  | `String`           | Время создания записи в базе API.             |

`LocationRef` содержит `name: String` и `url: String`. URL может не вести на полноценную локацию,
если место неизвестно; такую связь нужно отображать безопасно.

## REST API: Location

Маршруты:

- `GET /location` — страница локаций;
- `GET /location/{id}` — локация по ID;
- `GET /location/1,2,3` — несколько локаций;
- `GET /location?...` — поиск и фильтрация.

Query-параметры:

| Параметр    | Значение                  |
|-------------|---------------------------|
| `page`      | Номер страницы.           |
| `name`      | Поиск/фильтр по названию. |
| `type`      | Тип локации.              |
| `dimension` | Измерение.                |

Схема `Location`:

| Поле        | Тип                | Значение                                         |
|-------------|--------------------|--------------------------------------------------|
| `id`        | `Int`              | ID локации.                                      |
| `name`      | `String`           | Название.                                        |
| `type`      | `String`           | Тип, например планета или космическая станция.   |
| `dimension` | `String`           | Измерение; возможно значение `unknown`.          |
| `residents` | `List<String URL>` | Персонажи, которых в последний раз видели здесь. |
| `url`       | `String (URL)`     | URL самой локации.                               |
| `created`   | `String`           | Время создания записи в базе API.                |

## REST API: Episode

Маршруты:

- `GET /episode` — страница эпизодов;
- `GET /episode/{id}` — эпизод по ID;
- `GET /episode/1,2,3` — несколько эпизодов;
- `GET /episode?...` — поиск и фильтрация.

Query-параметры:

| Параметр  | Значение                                  |
|-----------|-------------------------------------------|
| `page`    | Номер страницы.                           |
| `name`    | Поиск/фильтр по названию эпизода.         |
| `episode` | Код эпизода в формате наподобие `S01E01`. |

Схема `Episode`:

| Поле         | Тип                | Значение                                                 |
|--------------|--------------------|----------------------------------------------------------|
| `id`         | `Int`              | ID эпизода; API сортирует эпизоды по ID в порядке серий. |
| `name`       | `String`           | Название эпизода.                                        |
| `air_date`   | `String`           | Дата выхода в текстовом формате API.                     |
| `episode`    | `String`           | Код сезона/серии, например `S03E07`.                     |
| `characters` | `List<String URL>` | Персонажи, появляющиеся в эпизоде.                       |
| `url`        | `String (URL)`     | URL самого эпизода.                                      |
| `created`    | `String`           | Время создания записи в базе API.                        |

## Связи ресурсов и загрузка деталей

API возвращает связи как полные URL, а не как вложенные объекты:

- `Episode.characters` → персонажи эпизода;
- `Location.residents` → персонажи локации;
- `Character.episode` → эпизоды персонажа;
- `Character.origin` и `Character.location` → краткие ссылки на локации.

Для связанных списков извлекать ID из URL и по возможности использовать endpoint нескольких ID, а не
выполнять отдельный запрос для каждого элемента. Нельзя рассчитывать на непустой список. Порядок,
предоставленный API, следует сохранять, если экран явно не задаёт другую сортировку.

## Функциональные требования

### Главный экран

- приветствие пользователя;
- краткий рассказ о мультсериале «Рик и Морти»;
- понятная навигация к эпизодам, персонажам и локациям.

### Эпизоды

- пагинируемый список эпизодов;
- поиск по названию через серверный параметр `name`;
- фильтрация по коду через серверный параметр `episode`;
- открытие экрана деталей эпизода;
- отображение названия, кода и даты выхода;
- на экране деталей сразу показать связанных персонажей: как минимум аватар, имя, статус/вид и
  переход к персонажу;
- пользователь может отметить эпизод просмотренным;
- пользователь может поставить оценку только от 1 до 5;
- пользователь может написать и изменить собственный комментарий;
- статус просмотра, оценка и комментарий сохраняются локально в Room и восстанавливаются после
  перезапуска;
- локальные пользовательские данные связывать со стабильным `episodeId`, не перезаписывать при
  обновлении сетевого кеша.

Рекомендуемая локальная сущность пользовательских данных: `episodeId` (primary key), `isWatched`,
`rating` (`null` либо 1–5), `comment`, `updatedAt`. Ограничение диапазона оценки проверять и на
уровне UI, и перед записью.

### Локации

- пагинируемый список локаций;
- серверный поиск/фильтры `name`, `type`, `dimension`;
- экран деталей с названием, типом и измерением;
- на экране деталей показать жителей с аватаром, именем и основной информацией;
- переход от жителя к экрану персонажа.

### Персонажи

- пагинируемый список персонажей;
- серверный поиск и все документированные фильтры `name`, `status`, `species`, `type`, `gender`;
- экран деталей с аватаром, именем, статусом, видом, типом, полом, происхождением и последней
  локацией;
- показать связанные эпизоды и обеспечить переход к эпизоду;
- при доступной ссылке обеспечить переход к локации.

### Поиск и фильтры

- поиск и фильтрация выполняются через query-параметры API, а не только по уже загруженной странице;
- применять задержку (debounce) к текстовому поиску и отменять устаревшие запросы;
- при изменении запроса/фильтра начинать с первой страницы;
- отображать состояния загрузки, пустого результата и ошибки с возможностью повтора;
- состояние активных фильтров должно быть видно пользователю и не теряться при переходе в детали и
  назад.

### Кеширование и офлайн-поведение

- кешировать полученные персонажи, локации и эпизоды локально, чтобы повторное открытие показывало
  данные без ожидания сети;
- отдельно кешировать изображения средствами выбранной библиотеки загрузки изображений (memory +
  disk cache);
- использовать стратегию показа кеша с последующим обновлением из сети;
- при отсутствии сети показывать доступный кеш и явное сообщение, если данных нет;
- определить политику свежести/инвалидации кеша одинаково во всех архитектурных ветках;
- сетевой кеш API и пользовательские записи Room — разные наборы данных с разным жизненным циклом;
- обновление сетевых данных не должно удалять оценки, комментарии и отметки просмотра.

## Единые требования к реализациям

- Android/Kotlin; существующий UI проекта построен на Jetpack Compose, сохранять этот стек, если
  отдельно не согласовано иное;
- одинаковые экраны, навигационные сценарии, тексты, состояния загрузки/ошибки и правила кеширования
  во всех ветках;
- сетевые DTO не использовать напрямую как UI-модели или Room-сущности: преобразования должны быть
  явными в пределах выбранной архитектуры;
- не хранить в коде текущие значения `count/pages` и не считать их неизменными;
- корректно обрабатывать ротацию/пересоздание процесса и повторную доставку состояния;
- доступность: content description для значимых изображений, достаточный контраст, удобные области
  нажатия;
- тестировать как минимум преобразование DTO, фильтры/query-параметры, ограничения оценки,
  сохранение пользовательских данных и ключевой поток состояния выбранной архитектуры;
- не добавлять функции, которые требуют изменения удалённых данных: публичный API предоставляет
  только чтение.

## Target SDK 37

Проект осознанно использует `compileSdk = 37` и `targetSdk = 37`. Изменения поведения Android 17
проверены по официальной документации. В текущем каркасе нет reflection над внутренностями
`MessageQueue` или `static final`, SMS/OTP, доступа к локальной сети, Contacts Provider, фонового
аудио, Bluetooth RFCOMM и динамической загрузки native-кода, поэтому дополнительная миграция для
этих изменений сейчас не требуется.

При добавлении соответствующих возможностей в архитектурных ветках учитывать:

- `ACCESS_LOCAL_NETWORK` требуется для прямого доступа к устройствам в LAN;
- certificate transparency включена по умолчанию, а TLS может использовать ECH;
- нельзя изменять `static final` через reflection/JNI или полагаться на private API `MessageQueue`;
- для фонового аудио действуют более строгие lifecycle/foreground-service требования;
- SMS с OTP, Contacts Provider, native dynamic code loading и Bluetooth RFCOMM имеют новые правила;
- ограничения ориентации, aspect ratio и resizability на больших экранах больше нельзя вернуть;
- каждый реализованный пользовательский поток тестировать на Android 17 до выпуска ветки.

## Единая дизайн-система

- во всех архитектурных ветках использовать тему и токены из пакета `ui.theme`;
- светлая и тёмная палитры обязательны, динамические системные цвета не заменяют фирменную палитру;
- Russo One используется только для крупных display/headline-заголовков;
- Manrope используется для title, body, label, элементов управления и пользовательских комментариев;
- оба шрифта встроены локально, поддерживают кириллицу и доступны без сети;
- использовать семантические цвета Material 3 и `ExtendedColors`, не вставлять hex-цвета в экраны;
- использовать `RickAndMortyTheme.spacing` и `RickAndMortyTheme.shapes`, не размножать случайные
  значения отступов и радиусов;
- экран `DesignSystemShowcaseScreen` служит визуальным эталоном и может быть заменён стартовым
  экраном при начале реализации ветки.
- launcher icon — оригинальный знак портала на космическом фоне; сохранять adaptive foreground,
  background и отдельный monochrome-слой для тематических иконок Android.

## Критерии готовности каждой архитектурной ветки

- реализованы главный экран, списки и детали эпизодов, локаций и персонажей;
- работают серверные поиск, фильтры и пагинация;
- связанные сущности подгружаются и отображаются без N+1-запросов там, где возможен batch endpoint;
- Room сохраняет отметку о просмотре, оценку 1–5 и комментарий к эпизоду;
- сетевые данные и изображения кешируются, приложение полезно при повторном запуске без сети;
- представлены loading/content/empty/error/offline состояния;
- архитектура соответствует названию ветки и не подменена другой архитектурой;
- проект собирается, автоматические тесты проходят;
- README ветки объясняет структуру и ключевые архитектурные решения.
